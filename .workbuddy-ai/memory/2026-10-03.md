**发现并堵上的静默失败陷阱（重要）**

`rsna_v3.make_clips` 的 physical 分支写作：

```python

    ...physical...; return clips
# 否则掉进 legacy index 采样
```

即 `sampling_geometry` 导入失败时（`HAS_SG=False`），**physical 会静默退化成 legacy**，
A/B 两臂跑同一套采样 → 必然"持平" → 会被误判为 "physical 无收益"。
v3 在 `run_inference()` 里加硬断言：physical 模式下 `HAS_SG` 必须为 True，否则 BLOCKED。

**教训（写入项目记忆）**：改 Kaggle kernel 时，凡"导入失败会静默回退到旧行为"的开关，
必须显式断言，不能靠 try/except 的默认值。否则实验结论会被无声污染。

## EXP-017 v3 结果：又一次 BLOCKED，但门禁拦得对

`stage: smoke:dicom` / `reason: exp013 read 0/8 studies — DICOM read failure`

**新问题的真因：`num_workers=2` 导致的测量假象（不是 DICOM 读失败）**

日志显示 `hit=0/8 empty=0 avg_clips=0.00`。**关键在 hit 与 empty 同时为 0**：
若真读不到图，`empty` 应为 8（`_load_study` 在 clips 为空时 `n_empty += 1`）。
两者皆 0 ⇒ 计数器根本没被主进程读到 —— DataLoader 的 worker 进程各自持有一份 dataset 副本，
计数在 worker 里自增，主进程 `ds.stats()` 看到的永远是初始值 0。

**这是"结构级指标冒充行为级证据"的教科书案例**（见用户记忆《验证与排查的纪律》）：
`ds.stats()` 是结构计数器，不是行为证据。我在 smoke 门禁里拿它当判据，等于用坏掉的尺子量长度。
而且 EXP-016 训练时 `workers=0`，我在推理里改成 2 属于**无谓偏离训练配置**。

**v4 修复**

1. `num_workers=0`（同时对齐 EXP-016 训练配置），并加注释说明为何不能改
2. 新增 `probe_dicom()`：**主进程内直接调 `ds._load_study(uid)`**，绕过 DataLoader，
   报告 n_clips / clip_shape / nonzero_frac / pixel_mean / pixel_max —— 真正的行为级证据
3. smoke 门禁改为先跑 probe：`n_clips==0` 或 `nonzero_frac==0.0` 才 BLOCKED
4. 新增 train_series 三级目录结构诊断，把真实布局打进日志，避免下次靠猜

**待验证**：v4 是否通过 probe 门禁。若 probe 显示真实像素非零，则 v3 的 0/8 确为计数器假象，
DICOM 一直能读；若 probe 也报 0 clips，则是真路径问题，诊断输出会给出真实布局。

## EXP-017 v4 完成 — 结果与统计判定（本轮核心）

**产物**：`rsna_knee/_out/exp017_oof_ab/`（另存 `_out/exp017_pull/`）

**数值（已独立复算，逐位一致）**

- legacy macro AUC = 0.735873015873016
- physical macro AUC = 0.7604040404040404

- prediction correlation = 0.9195

**关键：+0.0245 与噪声不可区分（两项独立检验）**

- **配对置换检验**（per-study 随机交换两模型预测，N=20000）：
  null sd = 0.0579，obs/null_sd = **0.424**，p(|d|>=obs) = **0.7336**
- **Bootstrap**（按 target 重采样 gold studies，B=5000）：
  95% CI = **[-0.0812, +0.1207]**，P(delta>0) = 0.656

**delta 的构成（粒度分析）**

11 个 target 里 **6 个 delta 恰为 0.0000**。整份 +0.0245 全部来自 3 个净秩翻转：
MCL +1 步、Medial Meniscus +1 步、PF OA +2 步、Fracture +1 步、Contusion −2 步。
其中 MCL 与 Medial Meniscus 的 **n_pos = 1**，即 AUC 由单个正样本在 9 个负样本中的排位决定，
粒度 1/9 = 0.1111，delta 恰好等于一个秩步。

**结论：属用户定义的「情况 B：基本持平」**，严格说连"弱正向信号"都谈不上——CI 大幅跨零。

**测量工具本身的功效问题（重要，需向用户强调）**

validation 的 gold 仅 10 个/target（fold0 分到 58 个中的 10 个）。
macro delta 的 null sd 高达 0.058，**任何 0.02 量级的效应在这个 gold 集上都测不出来**。
这意味着：后续若继续用同一 gold 集做 fold0 A/B，同样会得到"测不出"的结果，
不能据此判断变量无效。**这是量具问题，不是实验问题。**

## 加前置体检：避免每次踩雷烧一小时

v3 的教训是「缺文件只在评测阶段才炸，而那时已经烧掉 400-800s 的 vLLM 启动」。所以在 v4 排队期间做了静态审查 + 前置检查。

### 静态审查发现的两个潜在风险
1. `container_setup.INSTALL_DEPS_SCRIPT = resolve_sandbox_setup_script()` 在**模块导入时**求值（`config=None`），只认硬编码路径，其中一条指向数据集 `metric/gemma-4-developer-agent-metric-data` —— **我没挂这个数据集**。好在它返回 None 时 harness 视为可选。
2. `sample_verification.resolve_task_snapshot()` 找不到快照时返回**全 None**（不抛异常）。它找 `snapshots/{instance_id}.tgz` 或 `snapshots/base_{clean_repo}.tgz`。比赛 `snapshots/` 有 129 个文件对应 129 个任务，命名大概率匹配，但**无法在本地验证**（本地只有 4GB 的不完整下载）。

- **仅警告**：graphs / embeddings 缺失、sandbox setup script 解析不到
- 顺便建好 `work_dir/results` 并做写入探测
