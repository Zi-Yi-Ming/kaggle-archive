## RSNA EXP-018 优先级 2：B 的 resume 静默空转 —— 根因是 lr 被归零

### 症状

Kernel B（跨 kernel 从 A 的 ckpt resume，续跑 epoch 2）跑完 COMPLETE，日志一切正常：
`[resume] epoch_done=1 global_step=8 rng_restored=True` → `epoch 2/2 loss 0.7028` → ckpt 已存。

但比对发现：

| | param_hash_final | optimizer_state_hash | epoch2 loss |
|---|---|---|---|
| A 的 epoch1.ckpt | `c8d7ea36…` | `63ee9353…` | — |
| **B 的 epoch2.ckpt** | **`c8d7ea36…`（与 A 完全相同）** | `d038b2dc…`（变了） | 0.702834845 |
| C 的 epoch1.ckpt | `c8d7ea36…` | `63ee9353…` | — |
| C 的 epoch2.ckpt | `ad670a0d…` | `f6bf3c43…` | 0.702757791 |

即：B 的**模型参数一步没动**，但 optimizer 状态变了（step 计数器在走），loss 也照出。
C 的 epoch1 与 A 的 epoch1 逐位相同（权重与 optimizer 状态都一致），说明 A 写的 ckpt 起点是对的。

### 定位过程

1. `tests/repro_resume_param_change.py`（本地 CPU + 假数据，复刻 A→B 流程）**复现**：B resume 后参数与起点逐位相同。排除 Kaggle/CUDA 环境因素。
2. `tests/repro_resume_step.py` 逐步插桩，同一份 ckpt 两条路径各跑一步：
   - **P1** 初始化 → `load_state_dict` → 一步：`out.requires_grad=True`、`grad_L2=6.14e-02`（**梯度存在**）、`opt.step()` 后**无任何参数变化**。
   - **P2** 初始化 → 直接一步（不 load optimizer）：梯度同样存在，4 个参数全部变化。
   - → 病灶锁定在 `opt.load_state_dict(ck["optimizer_state_dict"])`。
3. 读 ckpt 里的 optimizer 参数组：
   - A 的 epoch1.ckpt：`lr = 0.0`，`scheduler.T_max = 1`，`last_epoch = 1`
   - C 的 epoch1.ckpt：`lr = 0.00015`，`scheduler.T_max = 2`，`last_epoch = 1`

### 根因

Kernel A 的脚本为了「只跑 1 个 epoch」，把 `args.epochs` 硬设成 1。于是
`CosineAnnealingLR(opt, T_max=args.epochs)` 的 **T_max 变成 1**。跑完 epoch 1 后
`sched.step()` 按余弦退火把 lr 从 3e-4 直接推到 `eta_min = 0`。这个 `lr = 0`
连同 `T_max = 1` 一起被写进 checkpoint。

B resume 时 `opt.load_state_dict` 忠实恢复了 `lr = 0`，`sched.load_state_dict` 也恢复了
`T_max = 1`。于是 B 的整个 epoch 2 **以 lr=0 训练**：前向照跑（所以 loss 有值）、
反向照跑（梯度非零）、`opt.step()` 里 Adam 的更新量 `lr * … = 0`（所以参数不动），
而 step 计数器仍递增（所以 optimizer 状态哈希变了）。

这同时解释了 loss 的微小差异：B 与 C 的 epoch2 起点权重相同、batch 顺序相同
（order hash 都是 `41407cc67dc16a6a`），但 C 在 epoch 2 内持续更新权重、B 不更新，
逐 batch 的 loss 逐渐分叉，epoch 平均值差 7.7e-5。

### 修复

改的是**测试脚手架**（Kernel A），不是 `rsna_v3.py`：

- `_push_exp018_resume_a/main.py`：删掉 `args.epochs = 1` 的 hack，改为跑满 `EPOCHS = 2`
  （与 B/C 一致 → scheduler 的 T_max 一致 → ckpt 里 lr 正确）。A 只发布 `epoch1.ckpt`
  给 B 用，不再发布 `latest.ckpt`（那是跑完 2 epoch 的状态，容易被误当 resume 点）。
- 新增硬闸门：A 检查 `ckpt.optimizer_state_dict.param_groups[0]["lr"]`，为 0 直接 `exit(1)`，
  不允许把 lr=0 的 ckpt 交给 B。
- `ckpt_info.json` 新增 `ckpt_lr` / `ckpt_scheduler_T_max` / `ckpt_scheduler_last_epoch`，
  并把 `param_hash_epoch1` 改为从 ckpt 的 `model_state_dict` 直接算（原来算的是 run_fold
  之后的最终模型，epochs 一变就名不副实）。

本地验证（`repro_resume_param_change.py`，A/B 都用 epochs=2）：
A 连续跑完 2 epoch 的最终 `param_hash = 8d034341`，B 从 A 的 epoch1.ckpt resume 续跑的最终
`param_hash = 8d034341` —— **两者相等，resume 等价性成立**；且 B 的 ckpt 里 lr = 0.00015 ≠ 0。

### 遗留的隐患（未改，待用户决定）

`run_fold` 的 resume 会从 ckpt 恢复 `lr`（来自 optimizer 的 `param_groups`）与 scheduler 状态。
若保存侧与恢复侧的 `epochs`（→ T_max）不一致，resumed 训练会**静默**使用错误甚至为零的 lr。
真实 EXP-018 的 resume 场景里两侧配置一致，所以不影响正式实验；但这类「配置漂移 → 静默空转」
值得在 `run_fold` 里加一条校验（例如恢复后断言 lr > 0，或校验 scheduler 的 T_max == args.epochs）。
未加的原因：改 `rsna_v3.py` 会改变代码 sha256（当前 `72832547`），使已完成的 C 失效，需 A/B/C 全部重跑。

### 纪律提醒

「跑完 + 日志正常 + 有 loss」不等于「训练真的发生了」。这次的判据必须是
**行为级的**：参数是否真的改变、resume 后的最终状态是否等于连续训练。仅看
`COMPLETE` 状态与 loss 数值会把空转误判为成功。

## RSNA EXP-018 smoke v1 失败：我自己把 ensure_torch 写坏了（已修）

### 报错

```
[smoke] preinstalled torch = 2.10.0+cu128; 强制替换为离线包
[smoke] mounted wheels = 13
  File "/kaggle/src/script.py", line 91, in ensure_torch
    import torch as _t
  File ".../torch/overrides.py", line 1635, in <module>
    has_torch_function = _add_docstr(
RuntimeError: function '_has_torch_function' already has a docstring
```

### 根因（两处，都是我自己加的）

1. 我在 `force_offline` 分支里先 `import torch` 只为打印预装版本 —— 这一步就把镜像
   预装的 2.10.0 C 扩展加载进了主进程。
2. 装完离线包后我又 `del sys.modules['torch']` 强行重新 import，于是 `torch/__init__.py`
   被二次执行，对进程里已存在的 C 函数重复 `_add_docstr` → RuntimeError。

更根本的一点：**主进程一旦 import 过 torch，即使 pip 卸载重装，当前进程仍持有旧模块**
（文件被删、模块在内存），后续代码会继续用旧版。所以「在主进程里 import 来校验版本」
这条路根本不成立。

原始 EXP-018 notebook 本来就是「先装、装完再首次 import」，是对的；是我加「硬闸门」
时画蛇添足，把 import 提前了。

### 修法

- 新增 `_torch_version_in_subprocess()`：用 `subprocess.run([sys.executable, "-c",
  "import torch;print(torch.__version__)"])` 在**独立子进程**里探测版本，装前装后各一次。
- `ensure_torch()` 去掉 `force_offline` 参数（smoke 恒为强制离线，留这个开关只会误用），
  全程不 import torch；返回后主进程才首次 `import torch`，拿到的必然是刚装好的版本。
- 断言装完的版本必须以 `2.2.0` 开头，否则 `BLOCKED` + `exit(1)`。

**通用教训**：任何「替换当前进程已加载的库」的操作，版本校验必须走子进程；
本进程内 `del sys.modules` + 重新 import 对带 C 扩展的包不可用。
