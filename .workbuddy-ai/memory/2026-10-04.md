## RSNA EXP-018 优先级 1+2：checkpoint / resume / 内存遥测

**背景**：EXP-018 v3（physical Axial fold0, n_clips 4→6）在 epoch 3 中途被 SIGKILL，`returncode -9`、wall 21970s（约 6.1h），零 artifact。此前 `run_fold` 只在**全部 epoch 结束后**才 `torch.save`，前两个 epoch 的成果一起丢失。诊断 kernel 已测出：300 studies 时 cache 1.191 GB、进程 RSS 2.56 GB、全折外推 17.5 GB（宿主 31.35 GB）；GPU 探针 0.545 GB reserved。H1–H4 全部仍为 UNPROVEN。

**本轮只改 4 类**（用户冻结其余全部变量）：checkpoint / resume / memory logging / diagnostic instrumentation。cache 逻辑未动。

### 改了什么（`rsna_knee/rsna_v3.py`，sha256 `bb1694cf3ef32faf0386300e58a0471579388624307233e576fa5696f4035d43`）

新增段「EXP-018: 真实训练内存遥测 / checkpoint / resume」+ `run_fold` 重写：

- `MemLogger`：后台线程每 N 秒采样，落 JSONL。字段含 `main_process_rss_gb` / `child_process_rss_gb` / `process_tree_rss_gb`（遍历 `proc.children(recursive=True)`，把 DataLoader worker 计入）/ `system_total/available/used_pct` / `torch_cuda_allocated/reserved/max_*` / `nvidia-smi`（memory.used + total + util）。峰值汇总写 `<diag_json>.summary.json`。
- `_save_ckpt_verified`：epoch 级 ckpt，含 model/opt/scheduler/epoch_done/global_step/experiment_id/config/runtime/rng/python·numpy·torch_cpu·torch_cuda RNG；写 tmp 再 `os.replace`（原子），**写后立刻读回校验**，校验不过抛 `_CkptWriteFailure`。每 epoch 写 `epoch{N}.ckpt` + `latest.ckpt`。
- `--resume-ckpt`：真 epoch resume，恢复上面全部状态，从 `epoch_done` 继续。与 `--resume-dir`（旧折级跳过）区分开。
- `--job-id`：作业状态文件（如 `/kaggle/working/exp018_job.json`），记录 `done_stages`，跨实例可见，用于判定是否还需继续跑。重读-改写-原子替换写。
- 新 CLI：`--resume-ckpt` / `--ckpt-dir` / `--diag-json` / `--mem-interval` / `--max-batches` / `--job-id`。

### 关键设计决定：DataLoader 必须显式传 generator

**原实现 `DataLoader(..., shuffle=True)` 未传 `generator`，`num_workers=0` 时 shuffle 退回 global RNG**，顺序变成「依赖训练过程消耗了多少随机数」，resume 无法复现。第一版我试图用「逐 batch 预热重放」绕过，结果 loss 差 0.0036——**因为预热自己又消费了一轮 RNG**。正确解法是 `_epoch_loader`：每 epoch 单独建 loader，`generator.manual_seed(seed*1000003 + epoch*7919 + shuffle)`，shuffle 顺序由 `(seed, epoch)` 唯一确定，与 global RNG 解耦，恢复 global RNG 后**无需预热**。

副作用（须如实记录）：这改变了 shuffle 的随机源。仍是随机 shuffle，训练语义不变，但 shuffle 序列与旧版不同。属于 checkpoint/resume 范围内的必要改动，已在报告中标注。

### ⚠️ 已暴露的流程错误（须避免重犯）

**Kernel A 用的代码 sha256 = `b9632015...`，B/C 用 `2414f84d...`，两者不一致。** 原因：A 在我本地修 `getattr` 之前就推了，数据集随后才 `datasets version` 到 v2。后果：**A/B/C 的比对不再严格**——虽然差异只是 `mem_interval`/`workers` 的 `getattr` 保护、不涉及 ckpt 序列化字段，但这是**未经证明的假设**，按纪律不得当作等价。

## RSNA EXP-018 优先级 2 收口：shuffle 语义回滚 + 统一 A/B/C 代码 hash

**触发**：用户指出我为修 resume 复现性引入的 per-epoch generator 改了 DataLoader 的随机源，把 EXP-016(control, 老 shuffle) vs EXP-018(treatment) 退化成双变量比较，单变量实验定义被悄悄破坏。这一处必须回滚。

**改动（`rsna_knee/rsna_v3.py`）**：

- `_epoch_loader` 回滚为 `DataLoader(ds, batch_size, shuffle=shuffle, num_workers, drop_last=False)`，**不传 generator**。shuffle 走 global RNG，与 EXP-016 control 完全一致。`epoch` 参数保留但只作日志标识。
- 新增 `loader_order_hash(loader, limit=8)`：对 DataLoader 实际吐出的前 8 个 batch 张量字节取 sha256。
- 新增 `probe_loader_order(ds, args, epoch, limit=8)`：用 `torch.random.fork_rng(devices=[])` + 手动存还原 `random`/`np.random` state，在 RNG 副本里取指纹，不干扰训练。
- `run_fold` 的 resume 顺序固定为：建 model/opt/sched/ds → `load_state_dict` → 恢复 epoch/global_step → **最后** `_restore_rng`。禁止先恢复 RNG 再建 model（model init 会消费 RNG）。
- epoch 循环内每 epoch 建 loader；`--loader-order-probe` 开启时记录 `loader_hashes`，写进 telemetry summary 与 stdout 的 `[order] epoch N loader_order_hash=...`。
- 新增 argparse：`--loader-order-probe`。telemetry summary 增 `loader_order_hashes`。

**本地 gate（rollback 后重跑）**：
